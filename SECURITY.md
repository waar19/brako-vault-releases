This self-contained document is the public security and transparency
statement for Brako Vault. The application source repository is private;
this public release repository does not provide source code or a
third-party reproducible-build claim. The published APK and its manifest
allow some claims below—such as signing identity and permissions—to be
checked manually. The assurance limits are stated in §12.

## 1. Encryption

| What | How | Parameters |
|------|-----|------------|
| Symmetric cipher | AES-256-GCM (NIST SP 800-38D) | 32-byte (256-bit) key, 16-byte (128-bit) authentication tag, 12-byte (96-bit) nonce per write |
| Key derivation | Argon2id (RFC 9106) | 64 MiB (65 536 KiB), 3 iterations, parallelism 4, 16-byte salt, 32-byte derived key |
| Salt per vault | Random, 16 bytes | Generated by a cryptographically secure random source on first creation |
| Nonce per write | Random, 12 bytes | 12 new bytes requested from Java `SecureRandom` for every write |
| Header | 50 bytes | The first 46 bytes are authenticated as Additional Authenticated Data (AAD); the final 4-byte `ciphertextLen` is not |

**What "tag" means.** AES-GCM produces a 16-byte authentication tag.
The tag authenticates the first 46 header bytes as AAD and the declared
ciphertext. Modification of that authenticated content causes
verification to fail. The 4-byte `ciphertextLen` is not authenticated,
and the current reader permits and ignores bytes after the declared
ciphertext; those bytes are not covered by the tag.

**What "nonce" means.** The 12-byte nonce is a value that must never
repeat under the same key. For every write, the app requests 12 new
bytes from Java `SecureRandom`. The implementation has no explicit
repetition detector and does not test whether the random source is
defective, so this is a probabilistic safeguard rather than a guarantee
of absolute uniqueness or a fail-closed check.

## 2. File format

All vault data is stored in a single file: `vault.bvda`.

Layout (big-endian for multi-byte fields, except `saltLen` and
`nonceLen` which are 1 byte):

```
 offset  size  field
 ------  ----  -----
   0       4   magic            = "BVDA" (ASCII)
   4       1   formatVersion    = 0x01
   5       1   kdfId            = 0x01 (Argon2id)
   6       1   aeadId           = 0x01 (AES-256-GCM)
   7       1   kdfParallelism   = 0x04
   8       4   kdfMemoryKiB     BE = 65 536
  12       4   kdfIterations    BE = 3
  16       1   saltLen          = 0x10 (16)
  17      16   kdfSalt
  33       1   nonceLen         = 0x0C (12)
  34      12   aeadNonce
  46       4   ciphertextLen    BE  <- NOT part of the AAD
  50       N   ciphertext (N = ciphertextLen, includes 16-byte tag)
```

The first 46 bytes of the header are the AAD. The tag is part of the
ciphertext. The authenticated region is therefore the first 46 bytes
plus the declared ciphertext and its GCM tag. `ciphertextLen` is not
authenticated. The current reader permits and ignores trailing bytes
after the declared ciphertext.

## 3. Write replacement and durability limits

Every save uses a write-then-rename pattern. The app:

1. Writes the new vault to `vault.bvda.tmp`.
2. Synchronizes the temporary file's descriptor.
3. Tries `ATOMIC_MOVE` with replacement.
4. If that fails, tries a non-atomic move with replacement.
5. If that also fails, copies the temporary file over the destination
   and deletes the temporary file.

The directory is not synchronized. Only the first replacement method is
intended to be atomic; filesystem support determines whether it succeeds.
The move and copy/delete fallbacks do not guarantee atomic replacement.
Consequently, a crash or power loss can still leave an interrupted or
missing destination when a fallback is used, and the document does not
promise full crash durability.

## 4. Biometric key protection

When biometric unlock is enabled, the derived key is wrapped with a key
stored in Android Keystore. The Keystore key is non-exportable through
the Android API, requires `BIOMETRIC_STRONG`, and is configured to be
invalidated when biometrics are re-enrolled.

Hardware, TEE, or StrongBox backing depends on the device and its
Keystore implementation. The app does not request StrongBox and does not
verify that the key is hardware-backed. These properties must therefore
not be assumed for every supported device.

## 5. No password recovery

There is no recovery mechanism, no email reset, no recovery key, no
customer support that can unlock a vault. The master password is the
only key, and it is never stored, never transmitted, and never logged.
If you lose the master password, the vault is gone.

The author of this project cannot unlock your vault either.

## 6. Threat model — what Brako Vault protects against

The app is designed to protect against:

- Theft of the device while powered off, by an adversary without the
  master password and without the ability to bypass Android's disk
  encryption.
- Network-based attacks: the app has no `INTERNET` permission, so
  compromised network conditions cannot exfiltrate the vault.
- Modification of the authenticated BVDA content: changes to the first
  46 header bytes, declared ciphertext, or GCM tag are detected.
- Brute-force of the master password: Argon2id with 64 MiB and 3
  iterations makes each guess expensive; an offline attacker still
  needs to brute-force the password itself.

The app is **not** designed to protect against:

- A compromised or rooted device that runs while the vault is open.
  Once the master password is verified, the key is in memory and the
  process has access to plaintext.
- Shoulder-surfing, keyloggers, or malware running with the same UID
  as the app.
- Coercion: a determined attacker with physical access to an unlocked
  device can read the vault.
- A weak or reused master password. Argon2id slows down guessing but
  cannot make "123456" secure.
- Replay or rollback to an older, valid `.bvda`. AES-GCM authenticates
  content but does not establish freshness or version monotonicity.
- Changes to unauthenticated `ciphertextLen` or trailing bytes outside
  the declared ciphertext. Such changes may affect parsing, but are not
  covered by the GCM tag.
- Disclosure of an exported file's password or transfer through an
  untrusted channel.

## 7. Backups

The app exports a `.bvda` file in the encrypted vault format. Every
export requires the user to enter a password for that file. The user
may choose the master password or a different password; there is no
passwordless export. By default, the on-device backup system is disabled
to keep the vault out of `adb backup` archives and cloud backups.

## 8. Offline synchronization

Brako Vault has no server. Synchronization between devices works by
exchanging `.bvda` files through a channel of the user's choice (USB,
email, cloud storage, AirDrop-style share). The app never opens a
network socket, so the channel cannot be observed by the app itself.
The authenticated BVDA content is checked with AES-GCM on import, so
tampering within that authenticated region is detected. This does not
detect replay of an older valid file or changes to unauthenticated
length/trailing data described in §2.

## 9. Declared permissions

Starting with v0.4.0, the APK declares exactly three Android platform
permissions:

| Permission | Why |
|------------|-----|
| `android.permission.CAMERA` | To scan QR codes that contain 2FA tokens. The camera is used only when the user opens the QR scanner; frames are processed on-device and never stored. |
| `android.permission.VIBRATE` | To give haptic feedback on actions such as successful unlock or copy-to-clipboard. |
| `android.permission.USE_BIOMETRIC` | To allow optional biometric unlock, mediated by Android Keystore. The app does not access biometric data directly. |

The release workflow verifies this exact platform-permission set with
`aapt2`. AndroidX also adds the custom permission
`com.brakovault.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. It is a
private, signature-level permission, not an Android platform permission,
and grants no network access. v0.3.0 may show additional normal
permissions contributed by AndroidX.

The APK **did not and does not** declare `android.permission.INTERNET`.
There is no fallback, no "debug build only" exception, and no
third-party SDK that requests it. If a future feature would need network
access, the feature is reconsidered; the permission is not added.

## 10. How to verify that the APK has no INTERNET permission

You do not need to trust this document. You can verify on any device
or workstation:

```shell
# From the Android SDK build-tools:
aapt2 dump permissions brako-vault-vX.Y.Z.apk
# or
aapt dump permissions brako-vault-vX.Y.Z.apk
```

For v0.4.0 and later, the expected Android platform permissions are
exactly the three listed in §9. `aapt2` can additionally show the
private AndroidX permission described there. v0.3.0 may show other
normal permissions contributed by AndroidX. If
`android.permission.INTERNET` appears in any version, the APK does not
match this document; do not install it.

## 11. Binary provenance and signing

Every release is signed with the maintainer's release key. Starting with
v0.4.0, the release also includes `SIGNING-CERTIFICATE.txt` and
`SHA256SUMS.txt`. Earlier releases do not include these two files. To
inspect the APK locally:

```shell
apksigner verify --verbose --print-certs brako-vault-vX.Y.Z.apk
```

The official, canonical SHA-256 signing-certificate fingerprint is:

`8a725a09dbe2483e2cd39435dc53f0355900744c01c97a2e0a860d6118908fbb`

Starting with v0.4.0, the release workflow requires this fingerprint.
The SHA-256 fingerprint printed by `apksigner` must match both the value
above and `SIGNING-CERTIFICATE.txt`. Artifact hashes must match
`SHA256SUMS.txt`.

`SHA256SUMS.txt` and `SIGNING-CERTIFICATE.txt` have no separate
signature. They can detect corruption, but cannot by themselves detect
a compromised GitHub account or repository because an attacker could
replace them together with the artifacts. The APK signature plus the
anchored fingerprint above authenticate the APK; they do not
authenticate an AAB or BLF file.

## 12. Levels of assurance

The available evidence has distinct scopes:

- **Design statement.** This public document states the intended
  security design and exact parameters.
- **Internal testing.** Tests in the private source repository check
  canonical parameters in a private document and internal behavior.
  They do not establish that these public documents were inspected, nor
  that the published APK or its manifest was tested.
- **External manual verification.** Anyone can manually inspect a
  downloaded APK's certificate and declared permissions with the
  commands above, and from v0.4.0 can compare its hashes and certificate
  fingerprint with the two release files and the canonical fingerprint
  in this document, subject to the limits stated in §11.

Brako Vault has **not** received an external security audit,
certification, Common Criteria evaluation, or third-party penetration
test. No reproducible-build guarantee is made.

## 13. Reporting a vulnerability

For sensitive reports, use GitHub Private Vulnerability Reporting:
[report a vulnerability privately](https://github.com/waar19/brako-vault-releases/security/advisories/new).
Do not include sensitive security details in a public issue. For
non-sensitive questions, you may use the repository's public
[issues](https://github.com/waar19/brako-vault-releases/issues).
No fixed acknowledgement or remediation deadline is promised.
