This document describes how Brako Vault protects the data on your device.
Every factual claim here is either derived from the public
[canonical crypto parameters file](https://github.com/waar19/brako-vault/blob/main/docs/canonical-crypto.md)
of the source repository or verifiable directly from the published APK
and the application's manifest. Where a statement is "designed" but not
"audited", the document says so.

> **Source code is private.** The application source is not in this
> repository. The numbers, sizes, and protocols below are the
> authoritative public statement of what the app does. The release APK
> is built from the same code that contains the constants in
> `Argon2Spec` and `BvdaConstants` in the private repository.

## 1. Encryption

| What | How | Parameters |
|------|-----|------------|
| Symmetric cipher | AES-256-GCM (NIST SP 800-38D) | 256-bit key, 128-bit authentication tag, 96-bit nonce (12 bytes) per write |
| Key derivation | Argon2id (RFC 9106) | 64 MiB (65 536 KiB), 3 iterations, 4 lanes, 16-byte salt, 32-byte derived key |
| Salt per vault | Random, 16 bytes | Generated by a cryptographically secure random source on first creation |
| Nonce per write | Random, 12 bytes | Unique per write, never reused with the same key |
| Header integrity | Bound to ciphertext | 46 bytes of header authenticated as Additional Authenticated Data (AAD) |

**What "tag" means.** AES-GCM produces a 128-bit authentication tag
that is appended to the ciphertext. Any modification of the file
(magic, KDF parameters, salt, nonce, or ciphertext) makes the tag check
fail and the vault refuses to open.

**What "nonce" means.** The 12-byte nonce is a value that must never
repeat under the same key. The app generates a fresh random nonce for
every save. Reusing a nonce would be catastrophic; this is why the
implementation explicitly fails closed if the random source is broken.

## 2. File format

All vault data is stored in a single file: `vault.bvda`.

Layout (big-endian for multi-byte fields, except `saltLen` and
`nonceLen` which are 1 byte):

```
 offset  size  field
 ------  ----  -----
   0       4   magic            = "BVDA" (ASCII)
   4       1   formatVersion    = 0x01
   5       1   kdfId            = 0x01 (Argon2id)
   6       1   aeadId           = 0x01 (AES-256-GCM)
   7       1   kdfParallelism   = 0x04
   8       4   kdfMemoryKiB     BE = 65 536
  12       4   kdfIterations    BE = 3
  16       1   saltLen          = 0x10 (16)
  17      16   kdfSalt
  33       1   nonceLen         = 0x0C (12)
  34      12   aeadNonce
  46       4   ciphertextLen    BE  <- NOT part of the AAD
  50       N   ciphertext (N = ciphertextLen, includes 16-byte tag)
```

The first 46 bytes of the header are the AAD. The tag is part of the
ciphertext, so the file's authenticated content covers everything except
the 4-byte length field of the ciphertext itself.

## 3. Atomic writes

Every save uses a write-then-rename pattern. The app:

1. Writes the new vault to `vault.bvda.tmp`.
2. Calls `fsync` on the temporary file.
3. Calls `fsync` on the directory.
4. Atomically renames `vault.bvda.tmp` to `vault.bvda`.

If the device loses power or the app is killed between steps, the
previous `vault.bvda` is untouched and the temporary file is left as
garbage (cleaned up on the next successful save).

## 4. Biometric key protection

When biometric unlock is enabled, the derived key is wrapped with a
key stored in the Android Keystore. The Keystore-backed key:

- Never leaves the secure hardware when the device has a Trusted
  Execution Environment (TEE) or a StrongBox Keymaster.
- Is non-extractable by user-mode processes.
- Is invalidated when the user removes all device biometrics, changes
  the lock screen, or the device is factory-reset.

The biometric prompt is enforced by the OS; the app cannot bypass it.

## 5. No password recovery

There is no recovery mechanism, no email reset, no recovery key, no
customer support that can unlock a vault. The master password is the
only key, and it is never stored, never transmitted, and never logged.
If you lose the master password, the vault is gone.

The author of this project cannot unlock your vault either.

## 6. Threat model — what Brako Vault protects against

The app is designed to protect against:

- Theft of the device while powered off, by an adversary without the
  master password and without the ability to bypass Android's disk
  encryption.
- Network-based attacks: the app has no `INTERNET` permission, so
  compromised network conditions cannot exfiltrate the vault.
- Replay or modification of the vault file: any flip of a bit in the
  file is detected by the AES-GCM tag check.
- Brute-force of the master password: Argon2id with 64 MiB and 3
  iterations makes each guess expensive; an offline attacker still
  needs to brute-force the password itself.

The app is **not** designed to protect against:

- A compromised or rooted device that runs while the vault is open.
  Once the master password is verified, the key is in memory and the
  process has access to plaintext.
- Shoulder-surfing, keyloggers, or malware running with the same UID
  as the app.
- Coercion: a determined attacker with physical access to an unlocked
  device can read the vault.
- A weak or reused master password. Argon2id slows down guessing but
  cannot make "123456" secure.
- The user voluntarily exporting the unencrypted vault to a third party.

## 7. Backups

The app exports a `.bvda` file (the same encrypted format as the
on-disk vault). The exported file is encrypted with the same
master-password-derived key unless the user explicitly chooses
"export without password" — and in that case the app warns loudly
that the file is unprotected. By default, the on-device backup system
is disabled to keep the vault out of `adb backup` archives and cloud
backups.

## 8. Offline synchronization

Brako Vault has no server. Synchronization between devices works by
exchanging `.bvda` files through a channel of the user's choice (USB,
email, cloud storage, AirDrop-style share). The app never opens a
network socket, so the channel cannot be observed by the app itself.
The file is authenticated end-to-end by the same AES-GCM tag check, so
a third party that relays a tampered copy is detected on import.

## 9. Declared permissions

The APK declares exactly three permissions:

| Permission | Why |
|------------|-----|
| `android.permission.CAMERA` | To scan QR codes that contain 2FA tokens. The camera is used only when the user opens the QR scanner; frames are processed on-device and never stored. |
| `android.permission.VIBRATE` | To give haptic feedback on actions such as successful unlock or copy-to-clipboard. |
| `android.permission.USE_BIOMETRIC` | To allow optional biometric unlock, mediated by Android Keystore. The app does not access biometric data directly. |

The APK **does not** declare `android.permission.INTERNET`. There is
no fallback, no "debug build only" exception, and no third-party SDK
that requests it. If a future feature would need network access, the
feature is reconsidered; the permission is not added.

## 10. How to verify that the APK has no INTERNET permission

You do not need to trust this document. You can verify on any device
or workstation:

```shell
# From the Android SDK build-tools:
aapt2 dump permissions brako-vault-vX.Y.Z.apk
# or
aapt dump permissions brako-vault-vX.Y.Z.apk
```

The output must list only the three permissions in §9. If
`android.permission.INTERNET` appears, the file is not the official
APK — do not install it.

## 11. Binary provenance and signing

Every release is signed with the maintainer's release key. The
fingerprint is published in the release notes. To verify locally:

```shell
apksigner verify --verbose --print-certs brako-vault-vX.Y.Z.apk
```

The SHA-256 fingerprint of the signing certificate must match the
one in the release notes. The checksums of every artifact are in
`SHA256SUMS.txt` next to the binaries in the same release.

## 12. Levels of assurance

Brako Vault is offered with three explicit levels of assurance. They
are not the same thing:

- **Designed.** The architecture and the parameter choices in this
  document are what the author committed to. This is the weakest
  claim.
- **Automatically tested.** A test suite in the private source
  repository — `CryptoSpecDocTest` and the broader `jvmTest` and
  `androidApp:testDebugUnitTest` suites — runs on every push and
  verifies that the implementation matches the public statements
  here, including the cryptographic parameters and the absence of
  `INTERNET` in the manifest.
- **Externally audited.** Brako Vault has **not** been audited by an
  external party. The author makes no claim of external certification,
  common-criteria evaluation, or third-party penetration test. If a
  future audit is performed, its findings will be published here with
  date, scope, and the full report.

## 13. Reporting a vulnerability

If you find a vulnerability, please email
`security@brakovault.example` (replace with the real address when the
project makes it public). Do not file a public GitHub issue for
security-sensitive reports. The author commits to acknowledge within
72 hours and to provide a fix or a documented risk-acceptance within
30 days for confirmed issues.
