# Brako Vault — セキュリティと透明性

[English](../../SECURITY.md) | [Español](SECURITY.es.md) | [Português](SECURITY.pt.md) | [Français](SECURITY.fr.md) | [Deutsch](SECURITY.de.md) | [Italiano](SECURITY.it.md) | **[日本語](SECURITY.ja.md)** | [简体中文](SECURITY.zh-CN.md)

最終更新: 2026-09-05

本書は Brako Vault の公開セキュリティ・透明性声明です。ソース
リポジトリは非公開であり、本リリースリポジトリはソースコードも
第三者による再現可能ビルドも提供しません。APK の署名と権限は手動で
検証できます。保証範囲は §12 に記載します。

## 1. 暗号化

| 項目 | 方式 | パラメータ |
|------|------|------------|
| 共通鍵暗号 | AES-256-GCM (NIST SP 800-38D) | 32 バイト (256 ビット) 鍵、16 バイト (128 ビット) タグ、12 バイト (96 ビット) nonce |
| 鍵導出 | Argon2id (RFC 9106) | 64 MiB (65 536 KiB)、3 反復、並列度 4、16 バイト salt、32 バイト鍵 |
| 保管庫ごとの salt | ランダム 16 バイト | 作成時に暗号学的に安全な乱数源で生成 |
| 書き込みごとの nonce | ランダム 12 バイト | 毎回 Java `SecureRandom` に新しい 12 バイトを要求 |
| ヘッダ | 50 バイト | 先頭 46 バイトが AAD。末尾 4 バイトの `ciphertextLen` は未認証 |

**「タグ」とは何か。** AES-GCM の 16 バイトタグは先頭 46 バイトを
AAD として、宣言された暗号文とともに認証します。`ciphertextLen`
は未認証です。現行リーダーは宣言暗号文後のバイトを許可・無視し、
タグはそれらを保護しません。

**「nonce」とは何か。** 12 バイトの nonce は、同じ鍵の元で決して
繰り返してはならない値です。毎回 Java `SecureRandom` に新しい
12 バイトを要求しますが、明示的な重複検出や乱数源故障検査は
ありません。したがって確率的保護であり、絶対一意性や fail-closed
の保証ではありません。

## 2. ファイル形式

保管庫のデータはすべて単一ファイル `vault.bvda` に格納されます。

レイアウト (マルチバイトフィールドはビッグエンディアン。`saltLen` と
`nonceLen` は 1 バイト):

```
 オフセット  サイズ  フィールド
 --------  ------  --------
   0          4    magic            = "BVDA" (ASCII)
   4          1    formatVersion    = 0x01
   5          1    kdfId            = 0x01 (Argon2id)
   6          1    aeadId           = 0x01 (AES-256-GCM)
   7          1    kdfParallelism   = 0x04
   8          4    kdfMemoryKiB     BE = 65 536
  12          4    kdfIterations    BE = 3
  16          1    saltLen          = 0x10 (16)
  17         16    kdfSalt
  33          1    nonceLen         = 0x0C (12)
  34         12    aeadNonce
  46          4    ciphertextLen    BE  <- AAD には含まない
  50          N    ciphertext (N = ciphertextLen、末尾に 16 B タグ)
```

認証範囲は先頭 46 バイトと、宣言された暗号文および GCM タグです。
`ciphertextLen` は未認証で、後続バイトは許可・無視されます。

## 3. 書き込み置換と耐久性の限界

すべての保存は「書いてから名前変更」のパターンに従います。アプリは:

1. 新しい保管庫を `vault.bvda.tmp` に書き出す。
2. 一時ファイルのディスクリプタを同期する。
3. 置換付き `ATOMIC_MOVE` を試す。
4. 失敗時は非アトミック move、さらに失敗時は copy+delete を使う。

ディレクトリは同期しません。最初の方法だけがファイルシステム対応時
にアトミックで、fallback は保証しません。障害時に宛先が不完全または
消失する可能性があり、完全なクラッシュ耐久性は保証しません。

## 4. 生体認証による鍵保護

派生鍵は Android Keystore 鍵でラップされます。この鍵は API から
エクスポート不可で、`BIOMETRIC_STRONG` を要求し、生体情報の再登録で
無効化されます。

ハードウェア、TEE、StrongBox 対応は端末依存です。アプリは StrongBox
を要求せず、hardware backing も検証しないため、全端末で保証されません。

## 5. パスワード復元なし

復元手段も、メールアドレスによるリセットも、復元鍵も、保管庫を
開けられるカスタマーサポートも存在しません。マスター
パスワードが唯一の鍵であり、保存されることはなく、送信される
ことはなく、ログに記録されることもありません。マスター
パスワードを紛失すると、保管庫も失われます。

本プロジェクトの作者であっても、あなたの保管庫を開くことは
できません。

## 6. 脅威モデル — Brako Vault が守るもの

このアプリは以下に対する保護を意図しています:

- 電源オフ状態の端末の盗難: マスター
  パスワードを持たず、Android のディスク暗号化を迂回する手段も
  持たない攻撃者からの保護。
- ネットワーク経由の攻撃: アプリには `INTERNET` 権限がないため、
  ネットワークが侵害されても保管庫を外部に持ち出すことは
  できない。
- 認証された BVDA 内容の改竄: 先頭 46 バイト、宣言暗号文、GCM タグ
  の変更を検出する。
- マスターパスワードへの総当たり: 64 MiB・3 反復の Argon2id が
  1 回ごとの推測を高コストにする。オフラインの攻撃者でも最終的に
  パスワードを推測する必要がある。

以下のことは **対象としていません**:

- 保管庫が開いている間に動作している、侵害済みまたは root 化された
  端末。マスターパスワードが認証された時点で鍵はメモリ上にある
  ため、プロセスは平文にアクセスできる。
- ショルダーハッキング、キーロガー、アプリと同じ UID で動作する
  マルウェア。
- 強要: アンロック済み端末への物理アクセスを持つ決意した攻撃者
  は保管庫を読める。
- 弱く再利用されているマスターパスワード。Argon2id は推測を遅く
  するが「123456」を安全にはしない。
- 古い有効な `.bvda` のリプレイやロールバック。AES-GCM は新しさや
  バージョン単調性を保証しない。
- 未認証の `ciphertextLen` や後続バイトの変更。
- エクスポートパスワードの漏洩や信頼できない転送経路。

## 7. バックアップ

すべての `.bvda` エクスポートで、ユーザーがパスワードを入力します。
マスターパスワードでも別のものでも構いません。パスワードなしの
エクスポートはありません。端末バックアップは既定で無効です。

## 8. オフライン同期

Brako Vault にはサーバーがありません。端末間の同期は、ユーザが
選んだチャネル(USB、メール、クラウドストレージ、AirDrop 風
共有)を通じて `.bvda` ファイルを交換する形で行われます。アプリは
ネットワークソケットを開かないため、チャネル自体をアプリが
観察することはできません。インポート時に AES-GCM が認証領域を
検証しますが、古い有効ファイルのリプレイや §2 の未認証データは
検出しません。

## 9. 宣言された権限

v0.4.0 以降、APK が宣言する Android プラットフォーム権限は正確に
次の 3 つです:

| 権限 | 理由 |
|------|------|
| `android.permission.CAMERA` | 2FA トークンを含む QR コードをスキャンするため。カメラはユーザが QR スキャナを開いたときだけ使用され、フレームは端末上で処理され、保存されることはない。 |
| `android.permission.VIBRATE` | ロック解除成功やクリップボードへのコピーといったアクションの触覚フィードバックのため。 |
| `android.permission.USE_BIOMETRIC` | 任意の生体認証ロックを、Android Keystore を介して可能にするため。アプリは生体データに直接アクセスしない。 |

リリースワークフローは、このプラットフォーム権限の組み合わせを
`aapt2` で検証します。AndroidX はさらにカスタム権限
`com.brakovault.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` を
追加します。これはアプリ専用の署名レベル権限であり、Android
プラットフォーム権限でもネットワークアクセス権限でもありません。
v0.3.0 では、AndroidX による追加の normal 権限が表示される場合が
ありました。

APK は過去も現在も `android.permission.INTERNET` を
**宣言していません**。フォールバックも、「デバッグビルドのみ」の
例外も、それを要求する第三者 SDK もありません。将来追加する機能で
ネットワークアクセスが必要になった場合は、その機能自体を見直し、
権限は追加しません。

## 10. APK に INTERNET 権限がないことを確認する方法

このドキュメントを信用しなくても構いません。任意の端末または
ワークステーションで以下を実行して検証できます:

```shell
# Android SDK build-tools から:
aapt2 dump permissions brako-vault-vX.Y.Z.apk
# または
aapt dump permissions brako-vault-vX.Y.Z.apk
```

v0.4.0 以降で期待される Android プラットフォーム権限は、§9 の
3 つだけです。`aapt2` には、同節で説明した AndroidX のアプリ専用
権限も表示される場合があります。v0.3.0 では AndroidX による他の
normal 権限も表示される場合がありました。どのバージョンでも
`android.permission.INTERNET` が表示された場合、その APK は本書と
一致しないため、インストールしないでください。

## 11. バイナリの来歴と署名

各リリースはメンテナ鍵で署名されています。v0.4.0 以降は
`SIGNING-CERTIFICATE.txt` と `SHA256SUMS.txt` も含みます。それ以前
にはありません。ローカル検証:

```shell
apksigner verify --verbose --print-certs brako-vault-vX.Y.Z.apk
```

署名証明書の公式かつ正規の SHA-256 指紋は次の値です:

`8a725a09dbe2483e2cd39435dc53f0355900744c01c97a2e0a860d6118908fbb`

v0.4.0 以降、リリースワークフローはこの指紋を必須としています。
`apksigner` が表示する SHA-256 指紋は、上記の値および
`SIGNING-CERTIFICATE.txt` の両方と一致し、成果物のハッシュは
`SHA256SUMS.txt` と一致する必要があります。

`SHA256SUMS.txt` と `SIGNING-CERTIFICATE.txt` には、それぞれを保護
する別個の署名はありません。ファイルの破損は検出できますが、
攻撃者が成果物とともに両ファイルを差し替えられるため、GitHub
アカウントやリポジトリの侵害そのものは検出できません。APK の署名と
上記の固定された指紋によって APK の真正性を確認できますが、AAB
または BLF ファイルの真正性は確認できません。

## 12. 保証レベル

証拠には異なる範囲があります:

- **設計声明。** 本公開文書が設計と正確なパラメータを示します。
- **内部テスト。** 非公開テストは非公開文書の正規パラメータと内部
  動作を検査します。本公開文書や公開 APK/manifest の検査証明では
  ありません。
- **外部手動検証。** 上記コマンドで証明書と権限を確認でき、v0.4.0
  以降は、ハッシュと指紋を 2 つのリリースファイルと照合し、指紋を
  本書の正規値とも照合できます。ただし §11 の制限が適用されます。

外部監査、認証、Common Criteria、第三者ペネトレーションテストは
**未実施**です。再現可能ビルドも保証しません。
